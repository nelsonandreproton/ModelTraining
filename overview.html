1. O que este projeto faz

Objetivo

Demonstrar o pipeline completo de treino de um modelo de linguagem (LLM) em dados próprios em português — desde a criação do dataset até à exposição via API REST. O foco principal é o fine-tuning eficiente com LoRA, que permite adaptar um modelo poderoso com poucos dados e sem GPU.

Fine-tuning LoRA Pré-treino do zero Avaliação de modelos Inferência via API Dataset em português

Stack principal

Modelo base Qwen2.5-1.5B-Instruct (1.54B params) Fine-tuning LoRA via PEFT + TRL SFTTrainer Framework ML PyTorch + Transformers Datasets HuggingFace datasets (Arrow) API FastAPI + Uvicorn Dataset 620+ pares Q&A em português (expansível via Kaggle) Hardware CPU (use_cpu=True)

3. Fase de dados

create_dataset.py

Criação do dataset

Define 620+ pares instruction → response em português, cobrindo 20+ categorias temáticas (geografia, história, ciência, matemática, tecnologia, filosofia, saúde, cultura portuguesa, IA/ML, etc.). Guarda em formato Arrow, o formato nativo da biblioteca datasets da HuggingFace — eficiente para datasets tabulares e compatível com todos os trainers. Pode ser expandido com pares gerados automaticamente via generate_dataset.py (LM Studio local) ou generate_dataset_kaggle.py (Qwen2.5-3B na T4 do Kaggle) e filtrados pela pipeline de qualidade.

Estrutura de cada exemplo:
instruction: "Qual é a capital de Portugal?"
response: "A capital de Portugal é Lisboa."
Porquê 620+ exemplos? Abaixo de ~50 exemplos o LoRA apenas memoriza os dados sem generalizar. 620+ exemplos diversificados permitem ao modelo aprender padrões de resposta em português em vez de decorar exemplos específicos. O dataset é expandível com pares gerados via Kaggle (Qwen2.5-3B) e filtrados automaticamente — placeholders não preenchidos, pares fora de tema Portugal e instruções truncadas são rejeitados antes da fusão.
explore_dataset.py

Processamento e formatação

Carrega o dataset raw, aplica um template de chat que transforma os pares instruction/response numa única string formatada, e divide em conjuntos de treino e teste. Este formato é o que o modelo irá ver durante o treino.

Template aplicado (Qwen ChatML):
<|im_start|>user
Qual é a capital de Portugal?<|im_end|>
<|im_start|>assistant
A capital de Portugal é Lisboa.<|im_end|>
ParâmetroValorSignificado
split 80% / 20% 400 exemplos para treino, 100 para avaliação. O teste permite medir se o modelo generaliza ou apenas memoriza os dados de treino.
template Qwen ChatML (<|im_start|> / <|im_end|>) Formato nativo do Qwen2.5-Instruct que ensina o modelo a distinguir perguntas de respostas. Usar o formato correto para o modelo base é essencial — template errado = resultados degradados.
tokenize_dataset.py

Tokenização

Converte o texto em sequências numéricas (IDs de tokens) que o modelo consegue processar. O Qwen2.5 usa Byte-Pair Encoding (BPE): começa com caracteres individuais e funde os pares mais frequentes, criando um vocabulário de 151 936 tokens (muito maior que o GPT-2 com 50 257 — melhor cobertura de português e caracteres especiais).

ParâmetroValorSignificado
max_length 512 tokens Tamanho máximo de cada exemplo. Antes era 128, o que truncava muitas respostas a meio. 512 permite respostas completas sem cortes, ao custo de mais memória RAM durante o treino.
truncation=True ativo Se um exemplo ultrapassar 512 tokens, é cortado. Necessário para manter tamanhos uniformes no batch.
padding="max_length" ativo Exemplos mais curtos que 512 tokens são preenchidos com o token especial EOS até atingir 512. Garante que todos os exemplos num batch têm o mesmo tamanho, requisito do PyTorch.
pad_token = eos_token 151645 O Qwen2.5 usa o token <|endoftext|> (ID 151645) como EOS. Reutilizamo-lo como padding. A attention_mask garante que estes tokens de padding são ignorados durante o treino.
padding_side "right" Qwen2.5 requer padding à direita (ao contrário de alguns modelos que fazem padding à esquerda). Padding errado degrada a qualidade do treino em modelos causais.

4. Fase de treino

finetune_lora.py
Caminho principal

Fine-tuning com LoRA

Parte do GPT-2 já treinado pela OpenAI em centenas de gigabytes de texto. O LoRA não altera os 124M parâmetros originais — adiciona apenas pequenas matrizes (adaptadores) nas camadas de atenção. O gradiente flui só pelos adaptadores, tornando o treino muito mais rápido e leve.

Qwen2.5-1.5B Base
1.54B params — congelado
+
LoRA Adapters
2.18M params — treináveis
W' = W + ΔW  |  ΔW = B × A  |  apenas 0.14% dos parâmetros actualizados (2.18M / 1.54B)
ParâmetroValorSignificado
r (rank) 8 Dimensão interna das matrizes LoRA (A e B). Rank maior = mais capacidade de aprendizagem, mais parâmetros. 8 é um bom equilíbrio para datasets pequenos.
lora_alpha 16 Factor de escala do LoRA. Na prática, o LoRA aplica ΔW × (alpha/r). Com alpha=16 e r=8, a escala é 2 — amplifica a contribuição dos adaptadores.
lora_dropout 0.05 Regularização: 5% dos neurónios dos adaptadores são desligados aleatoriamente durante o treino. Reduz overfitting em datasets pequenos.
target_modules q_proj, k_proj, v_proj, o_proj Camadas de atenção do Qwen2.5 onde os adaptadores são inseridos: projeção de queries, keys, values e output. Nomes diferentes do GPT-2 (c_attn/c_proj) mas mesma função — capturar padrões de relação entre tokens.
num_train_epochs 20 Número de vezes que o modelo vê todo o dataset de treino. Mais épocas = mais aprendizagem, mas risco de overfitting. Aumentado de 10 para 20 com o dataset maior.
learning_rate 2e-4 Tamanho do passo de atualização dos pesos. 0.0002 é um valor típico para LoRA — maior que fine-tuning completo (onde 1e-5 é comum) porque só os adaptadores aprendem.
per_device_train_batch_size 2 Exemplos processados em paralelo por cada passo. Valor baixo imposto pela RAM disponível (CPU). Batch maior estabilizaria o treino mas requer mais memória.
max_length 512 Comprimento máximo das sequências no SFTTrainer. Deve corresponder ao valor usado na tokenização para não haver truncações adicionais.
eval_strategy epoch Avalia no conjunto de teste no final de cada época. Permite monitorizar overfitting em tempo real e o load_best_model_at_end=True guarda o melhor checkpoint.
use_cpu True Força o treino em CPU. Necessário neste ambiente (sem GPU). Lento, mas funcional para datasets pequenos.
pretrain.py
Caminho experimental

Pré-treino do zero

Constrói uma versão minúscula do GPT-2 com arquitetura personalizada e treina todos os pesos desde o início. Ao contrário do LoRA, este modelo não parte de nenhum conhecimento prévio — aprende tudo do dataset de 500 exemplos.

ParâmetroValorSignificado
n_embd 128 Dimensão do espaço de embeddings. O GPT-2 real usa 768. 128 reduz drasticamente os parâmetros, tornando o treino viável em CPU.
n_layer 4 Número de blocos Transformer empilhados. GPT-2 usa 12. 4 camadas são o mínimo para aprender alguma estrutura de linguagem.

Resultado esperado: Perplexidade muito alta. 500 exemplos são insuficientes para treinar do zero — um modelo precisa de centenas de GB de texto para aprender a língua. Este caminho existe para fins didáticos, para comparar com o LoRA.

Interpretação dos resultados
O LoRA atingiu 1.86 vs 22.72 do Qwen2.5-1.5B base — uma melhoria de 12×. A perplexidade de 1.86 é excecional — significa que o modelo prevê cada token com ~86% de certeza, praticamente a memorizar o formato Q&A. Para comparação, o GPT-2 + LoRA anterior atingiu 6.44 no mesmo dataset.

O Qwen2.5-1.5B parte já de uma base muito mais forte (1.54B params vs 124M do GPT-2, treinado em dados multilingues incluindo português), o que explica o salto de qualidade mesmo com os mesmos 500 exemplos.

6. Conceitos chave

LoRA — Low-Rank Adaptation

Em vez de actualizar todos os 124M pesos do GPT-2, o LoRA adiciona duas matrizes pequenas (A e B) em cada camada de atenção. O produto B×A representa a adaptação aprendida. O modelo base fica intacto e pode ser reutilizado com diferentes adaptadores.

W_orig (124M) — congelado, nunca muda
A ∈ ℝ^(d×r) e B ∈ ℝ^(r×d) — treináveis
W_out = W_orig + (B × A) × (alpha / r)
Vantagem prática: O ficheiro guardado (my_lora_model/) tem apenas ~tens de MB porque só guarda A e B. O Qwen2.5-1.5B base (3 GB) é carregado separadamente e os adaptadores são adicionados em memória. No HuggingFace Hub, só o adaptador é publicado.

SFT — Supervised Fine-Tuning

O modelo aprende a imitar os pares instrução→resposta do dataset. A loss é calculada apenas nos tokens do <|assistant|> (a resposta) — não na pergunta. Isso ensina o modelo a responder, não a repetir a pergunta.

Input: <|im_start|>user\nQual a capital?<|im_end|>\n<|im_start|>assistant\n
Target: A capital é Lisboa.<|im_end|>
Loss: cross-entropy token a token na resposta

Perplexidade

Métrica padrão para modelos de linguagem. Calcula quão bem o modelo prevê cada token do texto de teste. Derivada directamente da loss de treino.

Perplexidade = exp( H )   onde H = — (1/N) Σ log P(tᵢ)
Regra prática: Perplexidade 1 = perfeito (improvável). Perplexidade 10 = bom para texto específico. Perplexidade 100+ = modelo não adaptado ao domínio.

Parâmetros de geração (inferência)

Controlam como o modelo escolhe cada token durante a geração:

ParâmetroValorEfeito
temperature 0.7 Suaviza a distribuição de probabilidade. 1.0 = distribuição original. <1 = mais determinista. >1 = mais aleatório/criativo.
repetition_penalty 1.3 Penaliza tokens já gerados, reduzindo a probabilidade de os repetir. Evita loops como "Lisboa Lisboa Lisboa…"
no_repeat_ngram_size 4 Proíbe que qualquer sequência de 4 tokens consecutivos se repita no output. Complementa a repetition_penalty.
max_new_tokens 50 Número máximo de tokens gerados. Limita o comprimento da resposta.

10. Geração de dataset no Kaggle (5000 pares)

Contexto

O script generate_dataset_kaggle.py usa um Qwen2.5-3B-Instruct local numa GPU T4 do Kaggle para gerar 5 000 pares Q&A em PT-PT sobre Portugal. A geração é feita em sessões de 1 000 pares porque o Kaggle não persiste /kaggle/working/ entre sessões — é obrigatório fazer "Save Version" manualmente antes de fechar.

Limitação da API Kaggle: A API do Kaggle não consegue disparar a execução de um notebook. O botão "Run" tem de ser clicado manualmente na UI. O que a API consegue fazer é descarregar os outputs após a execução (kaggle kernels output <slug>).

  1. Abrir generate_dataset_kaggle.py
  2. Definir TEST_MODE = False
  3. Definir TARGET = pares actuais + 1 000

11. Melhorias possíveis

Ordenadas por impacto esperado na qualidade do modelo. As primeiras têm maior retorno com menor esforço.

1

Usar um modelo base em português

O GPT-2 foi treinado quase exclusivamente em inglês. Partir de um modelo já pré-treinado em português (ex: neuralmind/gpt2-large-portuguese ou um Llama derivado PT) daria uma vantagem enorme — o modelo já "sabe" português antes do fine-tuning.

alta prioridade mudança no model_name impacto muito alto
2

Treino em GPU

Remover use_cpu=True e correr numa GPU (mesmo modesta, RTX 3060 ou Google Colab T4). Permite batch size 8–16, treino 10–50× mais rápido, e viabiliza modelos maiores e mais épocas sem horas de espera.

alta prioridade remover use_cpu=True colab grátis disponível
3

Mais dados e maior diversidade

500 exemplos é um bom começo, mas os melhores resultados com LoRA aparecem entre 1 000–10 000 exemplos. Integrar datasets públicos em português (ex: datasets do HuggingFace Hub como portuguese_qa, Wikipedia PT, ou conversas reais) multiplicaria a diversidade sem esforço manual.

alta prioridade HuggingFace Hub datasets públicos PT
4

Gradient accumulation

Com CPU e batch size 2, o gradiente é muito ruidoso. Adicionar gradient_accumulation_steps=8 no SFTConfig simula um batch size de 16 sem consumir mais memória — acumula gradientes de 8 passos antes de atualizar os pesos. Melhora a estabilidade do treino.

impacto médio 1 linha de código
5

Learning rate scheduler

Adicionar lr_scheduler_type="cosine" e warmup_ratio=0.1. O scheduler começa com lr baixo (warmup), sobe ao máximo, e vai decrescendo suavemente (cosine annealing). Evita instabilidades no início e melhora a convergência no final.

impacto médio boa prática standard
6

Rank LoRA maior (r=16 ou r=32)

Com o dataset atual de 500 exemplos, rank 8 está adequado. Com um dataset maior (1 000+), aumentar para r=16 ou r=32 dá ao LoRA mais capacidade de aprendizagem. O custo é um ficheiro de adaptadores ligeiramente maior (~10–20 MB).

aumentar após mais dados ajustar lora_alpha = 2×r
7

Adicionar mais módulos LoRA

Atualmente apenas c_attn e c_proj têm adaptadores. Adicionar as camadas MLP (c_fc, c_mlp) aumenta a expressividade do fine-tuning. Útil quando o modelo precisa de aprender padrões de conteúdo, não só de atenção.

exploração mais params treináveis
8

Métricas de avaliação adicionais

A perplexidade mede fluência mas não qualidade das respostas. Adicionar BLEU, ROUGE-L, ou avaliação humana permitiria perceber se as respostas são factualmente corretas e não apenas fluentes.

avaliação mais rigorosa sacrebleu, rouge-score
9

Quantização do modelo (int8 / int4)

Usar bitsandbytes para carregar o GPT-2 em int8 ou int4 durante o fine-tuning (QLoRA). Reduz o consumo de memória a metade ou um quarto, permitindo modelos maiores em hardware limitado.

requer GPU QLoRA bitsandbytes
10

Eliminar o caminho "pré-treino do zero"

Os resultados confirmam que treinar do zero com 500 exemplos não é viável (perplexidade 7727). O código pode ser simplificado para focar exclusivamente no LoRA, reduzindo manutenção e confusão conceptual.

simplificação remover pretrain.py do pipeline principal
